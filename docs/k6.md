# 🚀 k6 Load Testing Challenge

## Overview

Project ini adalah playground untuk belajar **load testing, performance engineering, backend scalability, dan system design** menggunakan [k6](https://k6.io/).

Goal utamanya bukan sekadar mengetahui apakah API "kuat 2.000 user", tetapi memahami:

- Bagaimana API berperforma di bawah load
- Kapan sistem mulai mengalami degradation
- Apa bottleneck utama
- Bagaimana database memengaruhi performance
- Bagaimana horizontal scaling bekerja
- Bagaimana caching dan queue memengaruhi system
- Bagaimana sistem menghadapi traffic spike
- Bagaimana melakukan performance optimization berdasarkan data

---

Setelah menyelesaikan seluruh challenge, diharapkan dapat memahami:

# 📊 Performance Metrics

Setiap challenge sebaiknya mengukur metrics berikut:

| Metric           | Description                           |
| ---------------- | ------------------------------------- |
| RPS              | Requests per second                   |
| Throughput       | Jumlah request yang berhasil diproses |
| p50              | Median latency                        |
| p95              | Latency yang dialami 95% request      |
| p99              | Latency tail                          |
| Error Rate       | Persentase request gagal              |
| CPU              | CPU utilization                       |
| Memory           | Memory utilization                    |
| DB Connections   | Jumlah koneksi database               |
| DB Query Latency | Waktu query database                  |
| Cache Hit Ratio  | Persentase cache hit                  |

# Challenge 04 — Same Email Race Condition

### Objective

Menguji behavior sistem ketika banyak request melakukan registration dengan email yang sama secara bersamaan.

### Scenario

```text
2,000 concurrent requests

POST /register

{
  "email": "test@example.com"
}
```

### Expected Result

```text
1 request  → 201 Created
1,999      → 409 Conflict
```

### Must Have

Database harus memiliki unique constraint:

```sql
UNIQUE(email)
```

### Questions

- Apakah terjadi duplicate user?
- Apakah race condition dapat terjadi?
- Apakah API mengembalikan 409 atau 500?
- Bagaimana transaction behavior-nya?

# 🧠 Important Concepts

## Concurrent Users ≠ RPS

2,000 concurrent users tidak berarti:

```text
2,000 requests/sec
```

Misalnya setiap request membutuhkan 500ms, maka jumlah request per second dapat berbeda tergantung behavior workload.

Karena itu selalu dokumentasikan:

```text
VUs
Request Rate
Latency
Duration
```

# 🎓 Final Goal

Setelah semua challenge selesai, project ini seharusnya bisa menjawab pertanyaan:

> **"How many users can this system handle, what is the bottleneck, and what happens when we exceed its capacity?"**

Bukan hanya:

> "API-nya bisa menerima 2,000 request."

Tetapi:

```text
Capacity
   ↓
Breaking Point
   ↓
Bottleneck
   ↓
Root Cause
   ↓
Optimization
   ↓
Trade-off
   ↓
New Capacity
```

Itulah inti dari **performance engineering**.
